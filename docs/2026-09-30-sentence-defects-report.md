## 三、根因分析

三类缺陷**不是同一处的 bug，而是两条独立链路的共同后果**。

### 3.1 A / B 类根因：词表层「按词替换、不看搭配」

`src/engine/humanize-vocab.ts` 的 `VOCAB` 是 `原词 → 替身[]` 映射，替换按词长降序执行，**不解析句法环境**。当原词的替身是单音节动词、而原词在句中带补语或特定宾语时，搭配立即崩坏：

| 原词 | 替身 | 崩坏场景 | 实测输出 |
|---|---|---|---|
| `坚持` | `守住` | 后接趋向补语「下去/下来」 | 只要**守住下去** |
| `坚持` | `守住` | 后接动宾「学习/思考/努力」 | **守住学习**、**守住努力** |
| `通过` | `靠/借/用` | 后接动词短语「引入/采用/实现…」 | **借引入**视觉检测系统 |
| `驱动` | `拉着/拉动` | 作定语 | 数据**拉着**的决策模式 |

**词表层证据（可复核）**：全表 280 条中，**替身是单音节的有 28 条**，即 28 个潜在同类风险点：

```
促进→助  促使→让  打造→做/建  借助于→借/靠/用  力图→想  利用→用  契合→贴
切忌→别  切实→真  取得→见  全面→全  然而→但  实施→干  通过→靠/借/用
务必→得  应对→接  愈发→更  针对→就  征程→路  旨在→想  诸如→像  坐落于→在
```

**为什么既有守卫没拦住**：

- 项目已有 `fragmentCanStand()`（`humanize-vocab.ts`）挡"无主句切分"，但它管的是**切句**，不管**换词**；
- `scan-bugs` 的 `brokenSigs` 里 `["裸难接动词", /(者|人|们)难(?!以)/]`、`["添劲接动词", /添劲(减轻|提高|…)/]` 说明**这类"替身接动词"的病本来就已知**，但签名是逐条手写的——`守住下去`、`借引入` 这两条恰好没被写进去；
- 词表卫生测试（`scripts/scripts-logic.test.ts`）只校验"替身不得落入高危套话黑名单"，**不校验替身的搭配合法性**；
- `docs/history/quaiwei_v0516_子代理优化_20260817_2300.md:25` 记着「**保障→守住** 整条移除（名词位"提供保障"病句）」——**同一类问题在 2026-08-17 就发生过一次并被单点处置**，但处置方式是"删掉那一条"，没有形成通用守卫，所以一个月后 `坚持→守住` 又踩进来。

> 这是本报告最重要的一条：**修的不是"守住"这个词，而是"单音节替身无搭配校验"这个缺口。**

### 3.2 C 类根因：`fragmentCanStand` 的副词守卫只认带体标记的形式

切分型缺陷的入口是 `fragmentCanStand()`（`src/engine/humanize-vocab.ts:475`），它决定"逗号能否升级为句号（劈句）"。现有守卫有 4 条：

```js
if (PREDICATE_ONLY_START.test(s)) return false;                    // ① 光杆谓语
if (/^[让使帮叫][\u4e00-\u9fa5]{0,3}/.test(s) && !/^[让使帮叫](我|我们|…)/.test(s)) return false;  // ② 使役无主句
if (/^(?:也|还|更|又)[\u4e00-\u9fa5]{0,5}(?:着|了|过)/.test(s)) return false;   // ③ 副词+动词**带体标记**
if (/^(?:就|则|便|才)(?:必须|应该|应|需要|要|能|可以|会|将|得)/.test(s)) return false;  // ④ 条件主句
```

**③ 就是漏洞所在**：它要求副词后必须紧跟 `着/了/过`。而 `也能决定`、`正在成为`、`将推动` 这些**同属"副词承接前句主语"的结构，完全不带体标记**，于是被放行、被劈成独立句。

实测（`fragmentCanStand` 直接调用，不经引擎）：

```
"采用智能化系统的企业。"         → 可独立成句: true   ← 名词短语，无谓语
"随着人工智能技术的快速发展。"     → 可独立成句: true   ← 状语
"其生产效率平均提升了百分之三十。"  → 可独立成句: true   ← 光杆「其」起头
```

三个都返回 `true`，即函数认为它们都能独立成句——**这就是三类切分缺陷的共同闸门**。

**根因确证（反向实验，可复现）**：临时把 `fragmentCanStand` 改为 `return false`（全部否决，等于关掉所有劈句），再测同一批签名：

| 签名 | 干净态 | `fragmentCanStand` 全否决 |
|---|---|---|
| 动补不兼容替换（A） | 118/120 | **118/120（不变）** |
| 动宾不兼容替换（A） | 120/120 | **120/120（不变）** |
| 介词降级后接动词短语（B） | 113/120 | **113/120（不变）** |
| 引导语命题被切开（C） | 119/120 | **0/120** |
| 谓语状语被切出成句（C） | 120/120 | **0/120** |
| 谓语状语被切出成句·话题述题（C） | 120/120 | **0/120** |

**C 类三条全部归零、A/B 两类完全不动**——既证明 C 类缺陷 100% 经由 `fragmentCanStand` 这条闸门，也证明 A/B 类走的是另一条链路（§3.1 的词表替换），两者的修法互不影响。

> 关键洞察（与前一份 postmortem 同构）：**检测器依赖的特征（"副词后是否带体标记"）不是它声称要检测的对象（"该小句能否独立成句"）的稳定属性。**

### 3.3 为什么既有回归全绿却漏掉了

| 既有防线 | 为什么没拦住 |
|---|---|
| `v5.2 brokenSigs["使役无主句"]` = `/。(让|使|帮|叫)[^。]{2,}/` | 只枚举 4 个使役动词，**不含副词类承接** |
| `collapseIssues()` 差分探针 | 判据是"**尾部被砍 ≥2 字**的删减型塌缩"；C 类是"**逗号升级为句号**"的切分型，前后文字一字不少，差分管不到 |
| `v0.2` 组样本（周作人式论说文 + 3 段外部文本 + 公文样本） | 这些样本里**恰好好不含** `坚持+补语`、`通过+动词短语`、`…，也/正在+动词` 这三种结构，属于**样本覆盖盲区** |
| `check:release` 七道门禁全绿 | 门禁只测"已知签名"，未测"未知结构"——**绿灯的置信区间 = 样本的覆盖面**，不等于引擎安全 |

## 四、影响面

### 4.1 严重度

| 维度 | 判断 |
|---|---|
| 用户可见性 | **高**。输出直接交给用户/拿去送检，语法错误比"AI 味"更致命（`README` §深度去味「严禁编造」一节已确立同一原则："工具卖点是更自然，输出带语法错误会直接砸口碑"） |
| 触发概率 | **高**。A/B 类只要原文出现高频词+常见搭配即触发；C 类只要原文有"话题—述题"或"数据显示，X 的 Y，其 Z"结构即触发 |
| 可检测性 | **低**。本地 `aiScore` 对这类破坏**给低分/不变**（语法错误不是它的判别项），用户看到的降幅反而是"变好了"——与 `injectHumanTypos` 停用时的结论同构 |
| 对外真实性 | 伤害"去味后仍可读"的核心承诺 |

### 4.2 对既有结论的影响

- 不影响 `calibration-data.json` 的标定（标定点是 leverage 值，不校验语法）；
- 但**影响 `README` 「改写质量已到"人读自然"水平」这一表述的适用范围**——至少在这三类结构上不成立。本文档不修改该结论，仅提出应加限定；
- 与 `docs/external-judge-findings.md` 的发现方向**不同**：那边是"分数虚低/虚高"的口径问题，这边是**真的把句子写坏了**，性质更硬。

### 4.3 外溢范围实测

在项目自带评测语料 `scripts/eval/corpus.json` 的 **S2（保温杯商品文案）** 上，"谓语状语被切出成句"签名命中 **120/1920** 次（6.3%）——说明这类结构在真实商品/营销文本里很常见，而 `corpus.json` 是**当初为评测去味质量而建的**语料，此前从未被任何语法签名扫过。

## 五、处置

### 5.1 本次已做：进回归门禁（基线棘轮）

在 `scripts/scan-bugs.ts` 新增 **`v7.0` 组**，含 6 条签名 + 7 条金丝雀 + 一份基线表：

```js
// 主签名：当前已知的破坏量（只许改善）
const V7_BASELINE = {
  动补不兼容替换: 118,           // A
  动宾不兼容替换: 120,           // A
  介词降级后接动词短语: 113,      // B
  引导语命题被切开: 119,          // C
  谓语状语被切出成句: 120,        // C（饱和）
  "谓语状语被切出成句·话题述题": 120, // C（饱和）
};
// 金丝雀：同闸门、当前干净，给基线留出"能上升"的空间（见 §5.2）
// 力图+动词=80 / 促进+名词=58 / 针对+问题=44 / 取得+名词=86
// 通过+名词=0 / 话题述题·未饱和=0 / 引导语·未饱和=0
```

语义（与 `RHYTHM_BASELINE` / `regression-12samples.lock.json` 同范式）：

- 命中 ≤ 基线 → **通过**，打印"当前值/基线值"对照，不阻断 CI；
- 命中 > 基线 → **报违规**，退出码 1，并把首个失败样本落到 `artifacts/scan-bugs/`；
- **不提供**"自动调高基线"的便捷开关——要放宽必须改这个常量并说明理由（延用项目 `--rebaseline` 必须带原因的设计纪律）；
- 维护口子 `SCAN_UPDATE_V7_BASELINE=1` 只**打印建议值**，不自动写常量（照 `RHYTHM_BASELINE` 的做法）。

**红绿验证（已做，可复现）**：

| 验证 | 操作 | 结果 |
|---|---|---|
| 绿（基线正确） | 直接跑 | `v7=0`，退出 0 ✅ |
| 红（基线被压低） | `动补不兼容替换` 118→100 | 退出 1，摘要表列出该签名超基线 18 次 ✅ |
| 红（真实退化） | 移除 `fragmentCanStand` 守卫③ | 退出 1，`v5.2` 抓 13 次；施加更强退化时抓 161 次 ✅ |
| 探针自检 | 故意让最小复现输入命中签名 | 走 `·探针无效` 分支并计违规（防"永真式签名"） ✅ |

**这道门禁不能替代什么（重要）**：它测的是**已知坏写法**。本次三类缺陷之所以能活到 v0.9.18，正是因为签名是逐条手写的，而样本恰好不含这些结构。所以它是"防复发"而非"防未知"——**把判据从"枚举坏写法"换成"检查搭配合法性"才是通用解**（见 §5.3）。

---

这样处理的效果：**下一次有人再往词表里塞单音节替身，或再放宽切分守卫，这 6 条计数会抬头，门禁直接红。**

### 5.2 本次已做（续）：金丝雀输入，补上"饱和签名抓不到新退化"的缺口

**这是本次实现里自己发现的一个门禁设计缺陷，如实记录**：

上面 6 条主签名的计数是**饱和**的——C 类三条本来就是 119~120/120，也就是"每次运行都命中"。对基线棘轮来说，饱和意味着**计数只能降不能升**：未来如果有人在别处引入同类的谓语切分破坏，这 6 条计数上不去，门禁**看不见**。

验证方式（可复现）：临时把 `fragmentCanStand` 改成全部放行（`return true`，最大化劈句倾向），主签名计数**一条都没动**，倒是 `v5.2` 组抓到 161 次违规。

因此补了 **7 条金丝雀输入**（`v7Canary`）——同样走 `fragmentCanStand` 那条闸门的同类结构，但当前引擎处理得**还算干净**，计数远低于饱和：

| 金丝雀 | 当前命中/120 | 特性 |
|---|---|---|
| 力图+动词 | 80 | 有余量 |
| 取得+名词 | 86 | 有余量 |
| 促进+名词 | 58 | 有余量 |
| 针对+问题 | 44 | 有余量 |
| 通过+名词 | **0** | **最灵敏：任何上升即新退化** |
| 话题述题·未饱和 | **0** | **最灵敏** |
| 引导语·未饱和 | **0** | **最灵敏** |

效果：主签名负责"记录当前已知的破坏量、只许改善"，金丝雀负责"抓新的同类破坏"。两者合起来才是一道既有记忆、又有灵敏度的门禁。

**局限（不掩饰）**：金丝雀仍是**手写样本**，覆盖的是我已经想到的结构。真正的通用解是 §5.3 ① 的搭配守卫与 ② 的守卫扩展——**把判据从"枚举已知坏写法"换成"检查搭配合法性"**，才能不依赖有人先踩到坑。本次没做这一步。

### 5.4 执行记录（2026-09-30，C 类根因已修）

**② `fragmentCanStand` 的副词守卫：从"副词+体标记"放宽为"副词+谓语"** ✅

```diff
- if (/^(?:也|还|更|又)[\u4e00-\u9fa5]{0,5}(?:着|了|过)/.test(s)) return false;
+ // 上一条保留（带体标记的场景它更准），新增：
+ if (ADVERB_CONTINUATION.test(s)) {          // 正在|正|将|已|也|还|更|又|就|才|则|仍|都|并|同时
+   const head = s.slice(0, 10);
+   if (!SUBJECT_HINT.test(head) && PREDICATE_HINT.test(head)) return false;
+ }
```

**为什么加"副词与谓语之间不得有主语"这条约束**：副词起头也可能是**自带主语**的合法句
（「也有很多企业失败了」「正在推进的项目已经过半」），否决它们只是白丢一次劈句机会、不修任何病句。
守卫的失败模式就是过度否决，所以正向判据必须配反向豁免。

**`fragmentFrontCanStand` 补「的+名词」长名词短语判据**（治 C1「引导语命题被切开」）✅

```diff
+ if (NP_TAIL_RE.test(lastSeg) && !NP_PREDICATE_RE.test(lastSeg)) return false;
```

原判据只拦 **≤4 字**的短残片（「这套工艺」），而「采用智能化系统的企业」有 10 字、整段无谓语，
于是被放行、被劈成「数据显示，采用智能化系统的企业。」+「其生产效率…」。

**⚠️ 这一条踩了两次同一个坑（都写进代码注释了，防第三次）**：判"有没有谓语"**不能**用单字表。

| 尝试 | 判据 | 结果 |
|---|---|---|
| ① 复用现成的 `CLAUSE_PREDICATE_RE` | 单字符宽表，含「以」 | **守卫形同虚设**：签名仍 119/119，一动不动 |
| ② 换成单字情态窄表（是\|在\|有\|能\|会\|要…） | 含「能」 | **同样失效**：「智**能**化的企业」命中「能」被判成有谓语 |
| ③ 只收**体标记 + 双字谓词** | `[着了过]\|正在\|可以\|提升\|成为\|…` | ✅ 生效 |

中文名词内部大量嵌这类单字（智能化/机会/现有/要求/内在），单字谓词表在中文里根本不可用。
③ 的代价是单字谓词句（「这是最好的方式」的「是」）会被误判成无谓语 → 少切一次句；
这个方向的错误是安全的：**少切只损失一次去味机会，多切则产出病句残句**。
